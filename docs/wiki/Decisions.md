# Decisions

Why things are built the way they are. Newest at the bottom. Open questions are at the end.

| # | Date | Decision | Why |
|---|---|---|---|
| 1 | 2026-11-07 | Build the hosted product as a **Laravel port of the WordPress plugin**, in `web/`, and keep the plugin as it is | Reuses the plugin's proven booking, billing and waiver rules; PHP like the plugin; the plugin keeps serving single-studio sites |
| 2 | 2026-11-07 | **Path-based tenancy** (`/{studio}`) with **global users** and a role per studio | One login across studios; one domain and certificate; studios can't see each other's rows (scoped bindings) |
| 3 | 2026-11-07 | **Server-rendered Blade**, one hand-written stylesheet, no JavaScript build | Fast pages, SEO-friendly public schedules, nothing to compile, few moving parts |
| 4 | 2026-11-07 | **Host on Render** with Docker and a Blueprint | Netlify was tried first, but it can't run PHP. Laravel Cloud was considered; Render was chosen for one Blueprint covering web, worker, cron and Postgres |
| 5 | 2026-11-07 | **Resend** for email, sending from `mail.loftstudio.app` | Laravel has a built-in Resend mailer; a sending subdomain keeps the main domain's reputation separate |
| 6 | 2026-11-07 | Domain **loftstudio.app** (registered at Porkbun) for the site and email | loft.com was considered at the start; loftstudio.app was chosen |
| 7 | 2026-11-07 | **Stripe Connect with direct charges** into each studio's own account | Money goes straight to the studio; the studio handles refunds, disputes and payouts; an optional platform fee; Loft is never the merchant of record |
| 8 | 2026-11-07 | **Webhooks fetch objects by ID** in a pinned API version ([#7](https://github.com/CyberpunkAidy/loft-studio/pull/7)) | Stripe no longer offers old versions for new webhooks, and payload shapes change between versions; fetching also handles events arriving out of order |
| 9 | 2026-11-08 | **Accounts v2** to create and onboard studio accounts, everything else on v1 ([#8](https://github.com/CyberpunkAidy/loft-studio/pull/8)) | Stripe blocks v1 account creation for new platforms; v1 endpoints accept v2 accounts |
| 10 | 2026-11-08 | **Account deletion** cascades through the database, and cancels renewing Stripe memberships first ([#9](https://github.com/CyberpunkAidy/loft-studio/pull/9)) | A deleted person must never be charged again; nothing is deleted if Stripe can't be reached |
| 11 | 2026-11-08 | **A studio's only owner** hands the studio over or closes it when deleting their account; owners can make other owners ([#10](https://github.com/CyberpunkAidy/loft-studio/pull/10)) | A studio always has an owner, and the owner decides, rather than Loft guessing |
| 12 | 2026-11-08 | **Own logo and design system**: self-hosted fonts, Lucide icons, readable studio colors ([#11](https://github.com/CyberpunkAidy/loft-studio/pull/11)) | A distinct brand; no font CDN; any brand color stays accessible |

| 14 | 2026-11-08 | **Payment options:** use the methods each studio turns on in Stripe, and record in-person payments in Loft; **no** PayPal or Square integration, and no platform-held funds ([#13](https://github.com/CyberpunkAidy/loft-studio/pull/13)) | Covers how studios are actually paid without a second processor; holding funds would make Loft liable for refunds, disputes and losses |
| 15 | 2026-11-08 | **Comps are recorded** like payments, with an amount of 0, and can be voided | An audit trail of who gave what, and a way to undo mistakes |

| 17 | 2026-11-08 | **Keep Laravel.** Build the mobile app with React Native (Expo) against a Laravel JSON API | The proposed move to Next.js and Node would be a rewrite of a live, tested product, for nothing the roadmap needs. See [the comparison](#tech-stack-nextjs-and-node) |
| 18 | 2026-11-08 | **From the proposed Prisma schema, adopt rooms, apparatus owned by a room, and waitlist limits;** keep Loft's own schema for everything else (option A) | Rooms with a fire-code limit, and apparatus rigged in a room, model aerial studios better than the roadmap's first sketch. Loft already covers the rest more fully. See [the review](#a-proposed-prisma-schema) |
| 19 | 2026-11-08 | **Pause WordPress plugin releases.** Move the plugin to `plugin/` for reference, and remove the release checklist and zip script | Work is focused on the web app and the mobile app. The repository's root is now about the web app. Tags `v0.1.0` and `v0.1.1` remain, and the release tooling can be restored from git history |
| 20 | 2026-11-08 | **Keep signed waivers.** When an account is deleted, its waiver signatures stay with the studio, unlinked from the account, with the signer's and attendee's names and the exact text signed. A studio's owner can download every signed waiver, for example before closing the studio | Studios may need signed waivers as evidence of liability long after a member leaves; once a studio is deleted, nobody could reach records kept inside Loft, so the owner takes a copy instead. Built with roadmap step 1 |
| 21 | 2026-11-08 | **When a class uses apparatus, every booking takes a spot on one.** Members pick one or "No preference" (the one with the most spots free). The class's capacity still applies on top. Waitlist entries keep the apparatus they asked for. Rooms are optional, and room clashes are warnings, not booking rules | A spot on a silk is what an aerial student is really booking, and a numbered spot ("Silks 3") is what the instructor needs on the roster. Spreading "No preference" bookings keeps scarce apparatus for people who ask for it. Clashes can be deliberate (a shared room split in two), so staff decide. Built with roadmap step 2 |
| 22 | 2026-11-08 | **Domain events go in an outbox table written in the same transaction as the change; emails stay on in-process events for now.** Every studio email is logged with a dedupe key. Marketing email needs opt-in per studio; SMS consent comes with SMS. Nightly snapshots count only classes before the studio's local midnight | The outbox makes history complete (nothing recorded without its change, nothing changed without its record), which churn scoring needs, without a message broker. Moving working emails onto the relay would change their timing for no gain yet; automations will be the relay's first consumer. Dedupe keys make every sender safe to retry. Point-in-time snapshots keep a future model from learning from data it wouldn't have had. Built with roadmap step 3 |
| 23 | 2026-11-08 | **Automations are marketing.** Every automated email (after a first class, birthday, we miss you) goes only to members who opted in, with an unsubscribe link. One of each per studio, off until turned on. First-class follow-ups come from the outbox; birthday and win-back from the hourly run, from 10 AM studio time. Win-back reaches only members who lapsed in the past week | Studios write the text freely, so any of these can carry offers; treating all of them as marketing keeps every studio compliant (CAN-SPAM, and opt-in rules elsewhere) without reviewing content. Booking and payment emails stay transactional. The win-back window stops a studio's first switch-on from emailing everyone who ever left. Built with roadmap step 4 |
| 24 | 2026-11-08 | **SMS: each studio connects its own Twilio account** (when SMS is built), as it connects Stripe | Carriers register each business as its own brand (A2P 10DLC), so the studio is the brand either way. With its own account, the studio registers it, owns its number and pays for its texts; Loft doesn't need to register as a Twilio ISV or bill studios for messages. A Loft-managed account (Twilio subaccounts, registration through Twilio's API) stays possible later |
| 25 | 2026-11-08 | **The orders ledger records sales as Stripe charged them:** one order per paid one-time checkout and per paid membership invoice (renewals included), and one per in-person payment. Numbered per studio from 1001. In-person history is copied in; earlier online sales aren't | One place to answer "what did we sell, and for how much", whatever the channel, and the base for the point of sale. Using Stripe's amounts (after promotion codes and tax) keeps the books matching payouts. Online amounts before the ledger exist only in Stripe, so inventing them from plan prices would be wrong. Built with roadmap step 5 |
| 26 | 2026-11-09 | **The point of sale comes first, online shop and card readers after.** A server-rendered till with the cart in the staff session; paid in person as today. Stock is taken with a conditional update, so it never goes below zero. Sales tax is the studio's own rate (in thousandths of a percent), on taxable products only; plans aren't taxed. Voiding restocks and cancels plans | The till works with no new Stripe setup, so studios can sell merchandise straight away, and it settles products, stock and tax before checkout and readers depend on them. A conditional update (`stock >= quantity`) needs no locks and can't oversell. A flat rate is enough for selling in the studio; Stripe Tax can calculate it for online sales later. Built with roadmap step 6 (first part) |
| 27 | 2026-11-09 | **The online shop holds stock while members pay, and orders are picked up at the studio.** Starting checkout takes the stock and creates a pending order with no number; a 30-minute Stripe Checkout Session with `price_data` lines and the studio's rate as a Stripe Tax Rate; paid → numbered and waiting to be picked up; not paid → released and restocked. The hourly job settles checkouts whose webhook never came. Plans stay on their own Checkout | Holding stock means two members can't pay for the last tee. Numbering on payment keeps paid orders gapless and leaves abandoned carts out of sales. Stripe Checkout's shortest expiry (30 minutes) bounds how long stock is held. `price_data` avoids syncing products to Stripe; a Tax Rate charges exactly the till's rate. Asking Stripe hourly instead of subscribing to `checkout.session.expired` needs no change to each studio's webhook setup. Pickup avoids shipping and its tax. Built with roadmap step 6 (second part) |
| 28 | 2026-11-09 | **Card readers are Stripe Terminal, server-driven, on each studio's account.** One Terminal Location per studio (from its address); readers paired by code. Charging takes the stock in a pending order (plans granted when paid) and sends a card-present PaymentIntent (automatic capture, the platform fee as online) to the reader; the front desk's page refreshes and asks Stripe until it's paid, declined or cancelled; the hourly job settles sales left open. Refunds from Loft refund the whole sale, then void it | Server-driven needs no app or SDK at the front desk: any browser runs the till, and the readers sit on the studio's own Stripe account like its other payments (direct charges). A page that asks Stripe, plus the sweep, avoids subscribing each account's webhook to Terminal events. Granting plans only when paid means a declined card leaves nothing to undo. Tips, Interac and offline mode wait until a studio needs them. Completes roadmap step 6 |
| 29 | 2026-11-09 | **The mobile API is v1 under `/api/v1`, with Sanctum bearer tokens and the website's services.** One token per app install (no expiry; revoked by signing out, a password change or reset, or deleting the account); browser sessions never sign in to it. Studio routes are scoped to the studio like the website's. Errors have one shape with stable codes; booking, adding people, signing waivers and starting checkouts take an `Idempotency-Key`; long lists use cursor pages; times are UTC plus the studio's local time. Plans are bought on Stripe Checkout in an in-app browser. Push tokens are stored; sending comes later | Sanctum is Laravel's own, so tokens, abilities and revocation need no new service. The booking, waiver, checkout and join logic moved out of the web controllers into services first, so both front doors follow the same rules (principle 2). Stable codes let the app react (sign a waiver, buy a plan) without parsing messages; idempotency keys make mobile retries safe. Stripe Checkout keeps card details and Apple's rules out of the app: classes are services used in person. Built with roadmap step 7 |
| 30 | 2026-11-09 | **Contactless check-in starts with QR codes and NFC/RFID tags; biometrics wait.** Kiosks and readers have their own device tokens (hashed, revocable, one studio), separate from member tokens. Members' QR codes are signed with the app key and rotate every 30 seconds, so nothing is stored; tag UIDs are stored only as keyed hashes. A scan checks the person in to their class from an hour before it starts until it ends, through the same check-in rule as the front desk (waivers enforced, no override at a kiosk), and every scan is logged in `access_events`. The kiosk is a web page that works with readers and scanners that type what they read | QR and NFC need no special hardware or vendor: a tablet with a browser and a cheap USB reader is enough, and the API serves native kiosks and door controllers. Rotating signed codes defeat screenshots without a database lookup per code. Keyed hashes mean a copy of the database doesn't give out tag numbers. Biometrics bring consent and retention duties (BIPA, GDPR Article 9) and stay out until a studio needs them. Built with roadmap step 8 |

## Considered alternatives

### Tech stack: Next.js and Node

A stack was proposed on 2026-11-08: Next.js (React, TypeScript, Tailwind) for web, React Native (Expo) for mobile, a Node.js API (Next.js routes or NestJS), PostgreSQL with Prisma or Drizzle, Stripe Connect, Twilio and SendGrid.

**Decided: keep Laravel** (decision 17). Here's how it compared:

| Proposed | In Loft | Outcome |
|---|---|---|
| Next.js + TypeScript + Tailwind for web | Laravel Blade and a hand-written design system | Kept Blade. Public pages are already server-rendered and SEO-friendly. Revisit a React front end only if the dashboard needs heavy in-browser interactivity. |
| React Native (Expo) for mobile | No app or API yet | **Adopted** for the app, talking to a Laravel JSON API (`/api/v1`, Sanctum tokens). Share TypeScript types generated from an OpenAPI description of the API, rather than sharing server code. |
| Node.js API (Next.js routes, NestJS, Express) | Laravel 13 (PHP 8.3) | Kept Laravel. Booking, payment and waiver rules run on the server either way. |
| PostgreSQL with JSONB | PostgreSQL 16 | Same. JSONB is planned for event payloads, automation rules and churn features. |
| Prisma or Drizzle | Eloquent and Laravel migrations | Kept Eloquent |
| Stripe Connect, including Terminal | Stripe Connect (Accounts v2, direct charges) | Same. Stripe Terminal is planned for the point of sale. |
| Twilio for SMS | Not yet | **Adopted** for SMS. Start US A2P 10DLC registration early; it takes weeks. |
| SendGrid for marketing email | Resend for all email | Kept Resend. It already sends everything, and it offers broadcasts for marketing email. |

### A proposed Prisma schema

A Prisma schema was proposed on 2026-11-08, with `Studio`, `User` (one studio, one role), `Waiver` and `UserWaiver`, `Membership`, `Room`, `Apparatus`, `Class` and `Booking`.

**Decided: option A** (decision 18). Its rooms and room-based apparatus are folded into Loft's Laravel schema (see [Roadmap](Roadmap)); Loft's own model covers the rest.

| Proposed model | Loft | What differs |
|---|---|---|
| `Studio` | `studios` | Loft also stores the slug, currency, brand color, settings and Stripe account |
| `User` (one studio, one role) | `users` (one login everywhere) + `studio_users` (a role per studio) | Loft supports several studios per person, and an admin role |
| *(none)* | `attendees` | Family members; the proposal couldn't book a child |
| `Waiver`, `UserWaiver` | `waivers` (versioned), `waiver_signatures` | Loft records the version signed, the guardian who signed, the typed name, the drawing, the IP address and the expiry |
| `Membership` | `plans` (what's sold) + `entitlements` (what's held) | Loft has status, weekly limits, class scope, Stripe IDs and seasonal tuition |
| `Room` | none | **Adopted** |
| `Apparatus` (in a room) | none | **Adopted**, plus a per-class allocation and an optional item number |
| `Class` | `programs` + `class_sessions` | Loft separates the recurring class from its dated sessions; `waitlistCapacity` **adopted** |
| `Booking` | `bookings` | Loft records the attendee, late-cancel and no-show statuses, waitlist position, the plan that paid, the credit used, and timestamps |
| `User.churnRiskScore` | planned `member_risk_scores` | A separate table keeps history, the model version and the reasons |

Problems found in the proposal, for the record:
- **It wouldn't validate.** Most relations are declared on one side only, and the enums are missing.
- **Studio separation:** `studioId` is missing from `Membership` and `Booking`, and emails aren't unique per studio.
- **One user, one studio:** no admin role.
- **Waivers:** no versioning, so editing a waiver changes what people appear to have signed.
- **Bookings:** don't record what paid for them, which breaks credit refunds and late-cancel and no-show policies.
- **Overbooking:** there's no locking, and a booking can't point at one particular silk.
- **Money:** there's no money model for a point of sale or checkout.
